如果 Redis 主节点刚加锁成功，但还没来得及同步给从节点，主节点就宕机了，这时从节点被提升为新主节点。其他客户端可能又能重新加锁成功，于是就可能出现 **两个客户端同时认为自己持有锁** 的情况。

**跳表底层数据结构？跳表和b+树区别？**

跳表的底层结构是多层有序链表。每个节点除了保存 key、value 之外，还会维护一个 forward 指针数组，表示它在不同层级上的下一个节点。最底层链表包含所有数据，上层链表相当于索引，用来加速查找。查找时从最高层开始，能往右就往右，不能往右就下降一层，最终在底层找到目标。跳表通过随机层数来维持概率平衡，查询、插入、删除的平均时间复杂度都是 O(log n)。

跳表和 B+ 树的主要区别在于：跳表是链表加多级索引，B+ 树是多叉平衡搜索树；跳表通过随机层数维持平衡，B+ 树通过节点分裂和合并维持平衡；跳表实现简单，适合内存场景，比如 Redis ZSet；B+ 树节点可以和磁盘页对齐，树高低，磁盘 IO 少，所以更适合数据库和文件系统这类磁盘索引场景。两者都支持范围查询，复杂度一般都是 O(log n + k)。

**分布式服务 对接口做限流 实现思路？**

分布式服务对接口限流，核心是控制单位时间内进入系统的请求量，避免突发流量打垮服务。限流可以做在网关层、应用层和资源层。网关层适合做全局 QPS、IP、用户、租户限流；应用层适合根据业务参数做细粒度限流；资源层用于保护数据库、Redis、线程池、第三方接口等下游资源。

常见限流算法有固定窗口、滑动窗口、漏桶和令牌桶。固定窗口实现简单但有临界突刺问题；滑动窗口更平滑；漏桶可以稳定流出流量；令牌桶既能限制平均速率，又允许一定突发流量，所以实际使用比较多。

如果是单机限流，可以用 Guava RateLimiter、Semaphore、Sentinel 等；如果是分布式限流，需要多个服务实例共享限流状态，常见方案是网关统一限流，或者使用 Redis + Lua 实现全局计数器、滑动窗口或令牌桶。Lua 的作用是保证计数、过期、判断这些操作的原子性。

实际项目中，我会优先在网关做粗粒度全局限流，在应用层做用户、接口、热点参数等细粒度限流，并配合熔断、降级、缓存和 MQ 削峰。限流触发后可以返回 429、友好提示、降级结果，或者把请求异步排队处理。



**redis淘汰策略详细讲一下？**

Redis 淘汰策略是在设置了 `maxmemory` 后，内存达到上限并且有新的写入请求时触发的。它决定 Redis 是拒绝写入，还是删除一部分 key 来腾出空间。

常见策略可以分为三类：第一类是 `noeviction`，内存满了不淘汰，直接拒绝写请求；第二类是 `volatile` 系列，只从设置了过期时间的 key 中淘汰，比如 `volatile-lru`、`volatile-lfu`、`volatile-random`、`volatile-ttl`；第三类是 `allkeys` 系列，从所有 key 中淘汰，比如 `allkeys-lru`、`allkeys-lfu`、`allkeys-random`。

LRU 表示最近最少使用，优先淘汰最近很久没访问的 key；LFU 表示最不经常使用，优先淘汰访问频率最低的 key；TTL 策略会优先淘汰剩余过期时间最短的 key。需要注意的是，Redis 的 LRU 和 LFU 都不是完全精确实现，而是通过随机采样做近似淘汰，采样数量由 `maxmemory-samples` 控制。

实际项目中，如果 Redis 纯粹作为缓存，常用 `allkeys-lru` 或 `allkeys-lfu`；如果 Redis 中既有缓存又有重要数据，可以使用 `volatile-lru` 或 `volatile-lfu`，只让设置了过期时间的缓存 key 被淘汰；如果数据不能丢，就使用 `noeviction`，让写请求失败，由业务处理。

**Java反射理解，Aop设计思路？**

Java 反射是指程序在运行时动态获取类的信息，并且可以动态创建对象、调用方法、访问字段的一种机制。

把与业务无关但多个模块都会用到的公共逻辑抽取出来，通过切面统一增强，避免侵入业务代码。

Java 反射是运行时动态获取类信息、创建对象、访问字段、调用方法和读取注解的机制。它的核心入口是 Class 对象，常用 API 包括 Constructor、Field、Method。反射广泛应用在 Spring IOC、依赖注入、MyBatis、JSON 序列化、JUnit 等框架中。它的优点是灵活、解耦，缺点是性能比直接调用低，而且可能破坏封装，很多错误要到运行时才暴露。

AOP 是面向切面编程，核心思想是把日志、事务、权限、限流、监控这类横切逻辑从业务代码中抽离出来，通过代理统一增强。Spring AOP 中有连接点、切点、通知、切面、织入等概念。底层实现主要依赖动态代理，如果目标类实现了接口，可以用 JDK 动态代理；如果没有接口，可以用 CGLIB 生成目标类子类进行代理。

AOP 的设计思路是：启动时扫描切面，根据切点表达式判断哪些 Bean 需要增强，然后为这些 Bean 创建代理对象。业务调用时实际调用的是代理对象，代理对象在执行目标方法前后插入增强逻辑，比如开启事务、记录日志、权限校验等。反射为 AOP 提供了运行时方法调用能力，而动态代理则是 AOP 实现方法增强的关键机制。

**AOP失效**

AOP 失效的核心原因是调用没有经过 Spring 代理对象。Spring AOP 是基于动态代理实现的，只有通过代理对象调用方法，切面逻辑才会执行。

常见失效场景包括：第一，同一个类内部方法自调用，比如 `this.method()`，不会经过代理对象；第二，目标对象不是 Spring 容器管理的 Bean，而是自己 new 出来的；第三，方法是 private、final，或者类是 final，代理无法增强；第四，切点表达式没有匹配到目标方法；第五，事务场景下异常被 catch 掉没有抛出，或者抛出的是受检异常但没有配置 `rollbackFor`；第六，多线程场景下事务上下文不能自动传播，因为事务信息通常存在 ThreadLocal 中。

所以排查 AOP 是否失效时，我一般会先看这个对象是不是 Spring Bean，再看调用是否经过代理对象，然后检查方法修饰符、切点表达式、异常处理和事务传播配置。

**元空间OOM**

元空间 OOM 对应的错误是 `java.lang.OutOfMemoryError: Metaspace`。JDK 8 之后，永久代被移除，方法区主要由元空间实现，元空间使用的是本地内存，主要存放类元信息、方法信息、字段信息、运行时常量池相关信息以及类加载器相关数据。

元空间 OOM 的常见原因是类加载过多、动态生成大量代理类，或者 ClassLoader 泄漏。比如反复热部署、插件系统、自定义类加载器、CGLIB 动态代理、脚本引擎等场景，如果旧的 ClassLoader 无法被回收，它加载的类也无法卸载，元空间就会持续增长。

排查时可以看 GC 日志和类加载数量，比如用 `jstat -class` 观察 Loaded 和 Unloaded 的变化，也可以通过 dump 分析是否存在大量 ClassLoader 或动态代理类。解决上，一方面可以合理设置 `-XX:MetaspaceSize` 和 `-XX:MaxMetaspaceSize`，另一方面更重要的是排查类加载器泄漏，关闭线程池、清理 ThreadLocal、注销 JDBC Driver、释放自定义 ClassLoader，避免无限动态生成类。

**对比一下 CMS 和 G1**

CMS 和 G1 都是以降低 GC 停顿为目标的垃圾回收器，但 CMS 更偏老年代并发回收，G1 是面向整堆的分区化回收器，目标是可预测停顿时间。

```
CMS 和 G1 都是为了降低 GC 停顿而设计的垃圾回收器。CMS 主要作用在老年代，通常和 ParNew 搭配使用。它采用标记-清除算法，流程包括初始标记、并发标记、重新标记和并发清除，其中初始标记和重新标记会 STW，并发标记和并发清除可以和用户线程一起执行，所以停顿时间比传统 Full GC 短。
但是 CMS 的问题也比较明显，因为它是标记-清除算法，会产生内存碎片；并发阶段用户线程还在运行，会产生浮动垃圾；如果老年代空间不足或者回收跟不上分配，就可能发生 Concurrent Mode Failure，退化成 Full GC，停顿时间会很长。
G1 则是把堆划分成多个 Region，逻辑上仍然有新生代和老年代，但物理上不要求连续。G1 会通过并发标记统计各个 Region 的垃圾比例，然后优先回收收益最高的 Region，所以叫 Garbage First。它采用复制和整理的方式回收 Region，碎片问题比 CMS 更少，并且可以通过 -XX:MaxGCPauseMillis 设置期望停顿时间，因此停顿时间更可预测。
简单来说，CMS 是传统分代模型下的老年代并发标记清除收集器，优点是降低停顿，缺点是碎片和浮动垃圾；G1 是 Region 化的整堆收集器，优点是可预测停顿和更少碎片，更适合大堆服务端应用。
```

**G1 回收器的STW时间是如何控制的？**

把堆拆成很多 Region，每次不一定回收整个堆，而是根据停顿时间目标，选择一部分“回收收益最高”的 Region 来回收。

**详细解释 MySQL 的 MVCC机制是如何实现的？**

MVCC，全称 Multi-Version Concurrency Control，多版本并发控制。它的核心思想是：同一条数据在数据库中可以存在多个历史版本，读操作通过读取合适的历史版本来避免和写操作互相阻塞，从而提高并发性能。

1. 隐藏字段
2. undo log 版本链
3. Read View 读视图

在 InnoDB 的 MVCC 中，Undo Log 和 Read View 是两个核心组件。Undo Log 负责保存记录的历史版本，每行记录通过隐藏字段 `DB_ROLL_PTR` 指向 Undo Log 中的旧版本，从而形成一条版本链；而 `DB_TRX_ID` 记录最近修改该版本的事务 ID。

Read View 负责判断版本可见性。它会记录创建读视图时系统中活跃事务的 ID 列表、最小活跃事务 ID、下一个事务 ID 以及当前事务 ID。事务读取数据时，会拿记录版本上的 `DB_TRX_ID` 和 Read View 做比较，判断该版本是否对当前事务可见。

如果当前最新版本不可见，就通过 `DB_ROLL_PTR` 去 Undo Log 中找上一个历史版本，继续判断，直到找到一个可见版本。

所以可以总结为：Undo Log 解决“有没有历史版本可读”的问题，Read View 解决“应该读哪个历史版本”的问题。

**RC（读已提交）和 RR（可重复读）隔离级别下，Read View 的生成时机有什么不同？**

RC 是每次快照读都会生成新的 Read View；RR 是事务中第一次快照读生成 Read View，后续复用同一个 Read View。

**在 RR 隔离级别下，MySQL 是如何解决幻读问题的？**

快照读通过 MVCC 解决幻读，当前读通过 Next-Key Lock 解决幻读。

**为什么普通的快照读不需要加锁？**

它读的不是正在被修改的“最新数据”，而是根据 Read View 读取一个对当前事务可见的历史版本。

**事务提交时，Redo Log 和 Binlog 的写入顺序是怎样的？（两阶段提交）**

```
1. 写 Redo Log，并标记为 prepare 状态
2. 写 Binlog
3. 提交事务，把 Redo Log 标记为 commit 状态
```

**如果 Redo Log 写完了但 Binlog 没写完时发生了宕机，MySQL 会如何处理？**

1. InnoDB 扫描 Redo Log，发现这个事务处于 prepare 状态
2. MySQL 检查 Binlog 中是否有这个事务的完整记录
3. 如果 Binlog 没有写完，或者没有完整事务记录
4. 说明这个事务还没有真正提交成功
5. InnoDB 会回滚这个事务

**快速排序模板**

```java
public class QuickSort {
    public static void quickSort(int[] arr, int left, int right) {
        if (left >= right) return;
        int pivot = arr[left + (right - left) / 2];
        int i = left, j = right;
        while (i <= j) {
            while (arr[i] < pivot) i++;
            while (arr[j] > pivot) j--;
            if (i <= j) {
                int tmp = arr[i];
                arr[i] = arr[j];
                arr[j] = tmp;
                i++;
                j--;
            }
        }
        quickSort(arr, left, j);
        quickSort(arr, i, right);
    }
}
```



**索引失效的原因**

MySQL 索引失效的常见原因主要有：
 第一，对索引字段使用函数、表达式计算或发生隐式类型转换；
 第二，联合索引不满足最左前缀原则，或者范围查询导致后面的字段无法继续使用索引；
 第三，LIKE 使用左模糊匹配，例如 `%abc` 或 `%abc%`；
 第四，OR 条件中存在未建索引字段，或者使用 `!=`、`<>`、`NOT IN`、`NOT LIKE` 等选择性较差的条件；
 第五，查询命中数据量过大、字段区分度低、回表成本高，优化器认为全表扫描更划算；
 第六，ORDER BY、GROUP BY 的字段顺序和索引顺序不一致，也可能导致索引无法用于排序。

**在数据库中有逻辑删除的一行，如何保持唯一性？**

如果是主键 ID，逻辑删除不影响唯一性，因为主键约束天然保证唯一，删除标记不改变记录仍然存在的事实。
 如果是业务唯一字段，比如手机号、用户名、订单号，则需要考虑逻辑删除记录仍然占用唯一索引的问题。常见方案是建立联合唯一索引，例如 `(biz_key, deleted)`，并且 deleted 字段使用 0 表示未删除，删除后改成删除时间戳或原 ID，保证同一个业务字段只有一条未删除记录，同时允许保留多条历史删除记录。

**死信队列是怎么用的？**

死信队列主要用于兜底处理异常消息，比如消息消费失败、超过重试次数、消息过期、队列满了等场景。它的作用不是解决业务问题本身，而是把异常消息沉淀下来，方便后续补偿、排查和人工干预。

**什么时候消息会进入死信队列？**

1）消息被消费者拒绝

2）消息存活时间超过TTL

3）队列长度超过限制

**如何处理死信消息？**

能自动恢复的自动重试，不能自动恢复的记录、告警、人工介入，最终保证消息不丢、问题可追踪、业务可补偿。

死信队列中的消息不能简单丢弃，也不能无限重试。我一般会先消费死信队列，把消息体、业务类型、失败原因、重试次数等信息落库，然后根据异常类型分类处理。

对于下游服务超时、网络抖动这类临时异常，可以通过延迟重试队列做有限次数重试；对于参数错误、业务状态非法这类不可恢复异常，则直接标记失败并告警，交给人工处理。

同时要提供后台补偿能力，比如重新投递、修改后重投、标记已处理等。重新投递时还要保证消费者幂等，避免重复消费造成重复扣款、重复发券这类问题。

最后还需要对死信队列做监控和告警，比如堆积数量、增长速度、失败率等。否则死信队列只是把问题从主流程转移到了另一个队列，并没有真正解决问题。

**10000QPS，单机4核8G内存，5个接口，如何设置线程池的各个参数？**

所需线程数 = QPS × 平均RT（秒)

cpu密集型

核心线程数 = CPU 核数 + 1
最大线程数 = CPU 核数 × 2

io密集型的经验公式

线程数 = CPU 核数 × (1 + IO等待时间 / CPU计算时间)

线程池参数不能只根据 QPS 设置，需要结合接口 RT 和任务类型。可以先用并发数 = QPS × RT 估算系统需要承载的并发量。如果是 CPU 密集型，4 核机器核心线程数一般设置为 4 到 5，最大线程数 8 左右；如果是 IO 密集型，可以按照 CPU 核数 × 1 + IO等待时间 / CPU计算时间 估算，初始可以设置 corePoolSize 50、maximumPoolSize 100、队列 1000。

另外 5 个接口不建议全部共用一个线程池，核心接口、慢接口、外部调用接口应该隔离，避免互相拖垮。队列要用有界队列，不能无限堆积；拒绝策略一般配合限流、降级和监控。最终参数一定要通过压测观察 CPU、RT、队列长度、活跃线程数、拒绝次数来调整。

队列大小 ≈ 入口 QPS × 可接受的最大排队时间

**hashmap在rehash的过程中有写的请求会发生什么**

`ConcurrentHashMap` 在 rehash 扩容过程中，如果有写请求进来，不会直接阻塞整个 Map，也不会像 HashMap 那样导致结构破坏。JDK 8 中它通过 `sizeCtl` 控制扩容状态，通过 `transferIndex` 将迁移任务分段，让多个线程协助扩容。扩容时会创建 `nextTable`，迁移完成的桶会在旧表中放置 `ForwardingNode`，表示该桶已经迁移。如果写线程访问到未迁移的桶，就对桶头节点加锁后完成写入；如果访问到 `ForwardingNode`，说明桶已经迁移，它会调用 `helpTransfer` 帮助扩容，然后到新表中继续插入。整个过程没有全局锁，锁粒度是桶级别，因此并发性能较好。

**MySQL为什么用B+树不用别的？**

MySQL InnoDB 使用 B+ 树作为索引结构，主要是因为 B+ 树非常适合磁盘存储。相比红黑树，B+ 树的每个节点可以存放大量 key，扇出更大，树高更低，因此磁盘 IO 次数更少。相比 Hash 表，B+ 树不仅支持等值查询，还支持范围查询、排序、最左前缀匹配等数据库常见场景。相比 B 树，B+ 树的非叶子节点只存索引 key，不存完整数据，因此一个页能存更多索引项，树更矮；同时数据都在叶子节点，并且叶子节点通过链表连接，非常适合范围扫描。

**MySQL中一张表能存多少行数据**

MySQL 一张表没有一个固定的行数上限。以 InnoDB 为例，表数据是按照主键组织成聚簇索引 B+ 树的，能存多少行主要取决于单行大小、页大小、索引大小和磁盘容量。默认 16KB 页大小下，3 层 B+ 树通常可以支撑千万级别数据，如果数据继续增长，B+ 树会增加到 4 层，理论上可以支撑更大的数据量。

但实际工程中，限制往往不是“能不能存”，而是“查询、索引维护、备份恢复、DDL、分页”等操作是否还能接受。所以一般单表达到千万级别后就要重点关注索引设计和 SQL 优化，达到几千万甚至上亿行时，可能需要考虑分区表、冷热数据拆分、归档、分库分表等方案。

**sychronized和lock的区别**

`synchronized` 是 Java 内置关键字，由 JVM 管理锁的获取和释放，使用简单，异常时也会自动释放锁，适合大多数简单同步场景。

`Lock` 是 JUC 包下的锁接口，常用实现是 `ReentrantLock`，需要手动加锁和释放锁，一般要在 `finally` 中调用 `unlock()`。它相比 `synchronized` 更灵活，支持 `tryLock` 非阻塞获取锁、超时获取锁、可中断加锁、公平锁，以及多个 `Condition` 条件队列。

选择上，如果只是普通的临界区保护，我会优先使用 `synchronized`，因为代码简单且不容易出错；如果业务中需要超时等待、响应中断、公平锁，或者像生产者消费者模型那样需要多个条件队列，就会选择 `ReentrantLock`。

```
| 对比点   | synchronized       | Lock / ReentrantLock |
| ----- | ------------------ | -------------------- |
| 类型    | Java 关键字           | JUC 接口/类             |
| 锁释放   | JVM 自动释放           | 必须手动释放               |
| 异常处理  | 异常时自动释放锁           | 需要 finally 中 unlock  |
| 尝试获取锁 | 不支持                | 支持 tryLock           |
| 超时获取锁 | 不支持                | 支持 tryLock(timeout)  |
| 响应中断  | 不支持等待锁时中断          | 支持 lockInterruptibly |
| 公平锁   | 不支持设置              | 支持公平/非公平             |
| 条件队列  | wait/notify，单一等待队列 | 可创建多个 Condition      |
| 使用难度  | 简单                 | 更灵活但更容易写错            |
| 推荐场景  | 简单同步               | 复杂并发控制               |

```

**synchronized 内部有没有锁升级的过程，详细讲讲？**

`synchronized` 内部有锁升级过程。JDK 6 之后 JVM 对 `synchronized` 做了优化，锁会根据竞争情况从无锁、偏向锁、轻量级锁逐步升级到重量级锁。

对象的锁状态主要存储在对象头的 `Mark Word` 中。没有竞争时，锁可以偏向第一个获取它的线程，后续同一线程再次进入几乎不需要同步操作；当出现其他线程竞争时，会撤销偏向并升级为轻量级锁，轻量级锁通过 CAS 和自旋来避免线程阻塞；如果竞争进一步加剧，自旋失败，就会升级成重量级锁，线程进入 Monitor 阻塞队列，由操作系统进行阻塞和唤醒。

**synchronized和lock的底层实现分别是怎么实现的**

`synchronized` 是 Java 关键字，不是普通类。它的实现主要依赖三部分：

1. 对象头中的 `Mark Word`
2. JVM 字节码指令
3. Monitor 监视器锁



AQS 是 `AbstractQueuedSynchronizer`，也就是抽象队列同步器，是 JUC 包中很多同步组件的底层框架。它的核心是一个 `volatile int state` 和一个 FIFO 双向等待队列。`state` 表示同步状态，比如在 `ReentrantLock` 中表示锁的占用和重入次数，在 `Semaphore` 中表示许可证数量，在 `CountDownLatch` 中表示计数值。线程获取资源时会通过 CAS 修改 `state`，如果成功就获取资源；如果失败，就会被封装成 Node 加入 AQS 队列，并通过 `LockSupport.park()` 阻塞。释放资源时会修改 `state`，并通过 `LockSupport.unpark()` 唤醒队列中的后继线程。AQS 支持独占模式和共享模式，`ReentrantLock` 是独占模式，`Semaphore`、`CountDownLatch`、读写锁的读锁是共享模式。

**TCP 三次握手为什么一定是三次，能不能两次？**

TCP 三次握手的目的主要有两个：第一，确认客户端和服务端双方的发送能力、接收能力都正常；第二，同步双方的初始序列号。

第一次握手，客户端发送 SYN，服务端收到后可以确认客户端发送能力和服务端接收能力正常。第二次握手，服务端返回 SYN + ACK，客户端收到后可以确认服务端发送能力和客户端接收能力正常。第三次握手，客户端再返回 ACK，服务端收到后，才能确认客户端确实收到了自己的 SYN，也就是确认客户端接收能力和服务端发送能力正常。

如果只有两次握手，服务端无法确认客户端是否收到了自己的 SYN + ACK，也无法确认客户端的接收能力是否正常。另外，两次握手还可能导致历史 SYN 报文问题：网络中滞留的旧连接请求到达服务端后，服务端可能误以为是新的连接请求并直接建立连接，造成资源浪费。而三次握手要求客户端必须返回最终 ACK，服务端才会真正建立连接，可以避免这种无效连接。

**TCP 作为可靠性协议，有哪些可靠性保障机制？**

TCP 通过 **序列号、确认应答、超时重传、快速重传、滑动窗口、流量控制、拥塞控制、校验和、连接管理、有序交付和去重机制** 来保证可靠传输。

TCP 的可靠性主要由几个机制保证。首先是序列号机制，TCP 会给字节流编号，用来保证数据有序、去重以及判断丢包。其次是 ACK 确认应答机制，接收方通过 ACK 告诉发送方哪些数据已经连续收到。第三是重传机制，包括超时重传和快速重传，数据或 ACK 丢失时可以重新发送。第四是滑动窗口，在保证可靠确认的同时提升传输效率。第五是流量控制，通过接收窗口防止发送方把接收方缓冲区打满。第六是拥塞控制，通过慢启动、拥塞避免、快速重传、快速恢复等机制控制发送速率，避免网络拥塞。除此之外，TCP 还有校验和、有序交付、去重，以及三次握手和四次挥手等连接管理机制，共同保证可靠传输。



**Mysql中的锁的类型**

| --------------------- | -------------------------- |

| Gap Lock              | 锁住两个索引记录之间的间隙 |
| Next-Key Lock         | 记录锁 + 间隙锁            |
| Insert Intention Lock | 插入意向锁，插入记录前使用 |



**什么是间隙锁：**

**间隙锁 Gap Lock** 只锁“两个索引记录之间的空隙”，不锁已有记录；**临键锁 Next-Key Lock** = **记录锁 Record Lock + 间隙锁 Gap Lock**，既锁已有记录，也锁记录前面的间隙。

**WebSocket 和 TCP 的关系是什么？**

WebSocket 和 TCP 的关系可以这样理解：

也就是说，WebSocket 不是 TCP 的替代品，而是**运行在 TCP 之上的一种应用层通信协议**。

**CompletableFuture 底层采用了什么机制？**

`CompletableFuture` 内部维护了一个 **volatile int 状态位**（`state`）和结果/异常引用。所有状态转换（未完成 → 完成 → 异常完成）都通过 **CAS（Compare-And-Swap）** 原子操作完成，避免使用重量级锁。

**CPU如何访问内存的？**

1. CPU 生成虚拟地址 →
2. MMU + TLB 翻译成物理地址 →
3. 缓存层次查询（L1 → L2 → L3） →
4. 未命中则内存控制器访问 DRAM →
5. 数据原路返回并填充缓存。

**PC中的CPU访问内存需要10ns吗，访问一个100m外的内存需要多久？**

**部分正确，但不精确。** 10纳秒（ns）更接近 **L3缓存** 的访问延迟，而不是主内存（DRAM）。

现代典型PC的内存访问延迟大致如下：

- **L1 缓存**：~1 ns（约 1-4 个 CPU 周期）
- **L2 缓存**：~4–10 ns
- **L3 缓存**：~10–40 ns
- **主内存（DRAM）**：**~60–100 ns**（通常在 80 ns 左右）

所以，**10 ns 可以访问到 CPU 内部较近的缓存，但无法访问主内存**。如果问的是“CPU 访问内存（主存）”，实际需要约 60–100 ns。



**JVM如何调优？**

1. **明确目标**：响应时间优先（如 web 服务）还是吞吐量优先（如批处理）？
2. **基准测试**：在典型负载下监控 GC、内存、CPU 等指标。
3. **发现问题**：频繁 Full GC、单次 GC 时间过长、内存持续增长等。
4. **调整参数**：根据问题类型修改 JVM 参数。
5. **验证效果**：重复压测，对比指标，避免过度调优。

1. 堆内存大小（最重要）
bash
-Xms<size>   # 初始堆大小，建议与 -Xmx 一致，避免动态扩容
-Xmx<size>   # 最大堆大小，根据物理内存与应用需求设置（如 4GB 堆留 1-2GB 给系统）
-XX:MaxMetaspaceSize=<size>   # 元空间上限（防止类加载泄漏）
2. 新生代比例
bash
-Xmn<size>          # 新生代大小（显式指定，或通过 -XX:NewRatio 设置）
-XX:SurvivorRatio=8  # Eden:Survivor 比例（默认 8:1:1）
-XX:+UseAdaptiveSizePolicy   # 开启自适应（让 JVM 自动调节，推荐）
建议：新生代尽量容纳应用 60%-80% 的短期对象，避免过早晋升到老年代。

三、常见问题场景与调优策略
1. 年轻代 GC（Minor GC）频繁
现象：GC 日志显示每分钟数十次，停顿时间很短。

调优：增大新生代（-Xmn）或提升 Eden 比例（-XX:SurvivorRatio）。

2. 老年代持续增长，Full GC 频繁
原因：内存泄漏、大对象直接进入老年代、晋升阈值太低。

调优：

检查是否有内存泄漏（MAT 分析 heap dump）。

增加老年代空间（-Xmx）。

调整晋升阈值：-XX:MaxTenuringThreshold=15（G1 可自动）。

使用 G1 或 ZGC 分散 Full GC 压力。

3. GC 停顿时间过长
G1 调优：设置 -XX:MaxGCPauseMillis 目标（如 100ms），但不要设得太小（否则 G1 过度频繁调整）。

ZGC：若 JDK 17+，直接启用 -XX:+UseZGC。

并行 GC：减少 -XX:ParallelGCThreads（默认 CPU 数，过多会竞争）。

4. CPU 使用率过高但 GC 正常
可能是代码效率问题（死循环、锁竞争），使用 profiler（如 AsyncProfiler）定位热点方法。
